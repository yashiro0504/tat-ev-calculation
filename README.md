### 근거가 된 관찰
- **Overwolf GEP TFT 문서**에 `opponent_board_pieces` 와 `board_spectate` 가 별도 항목으로 존재하고, 샘플 JSON에 여러 소환사별 `board`/`bench`(+성급, 아이템 3칸)가 들어 있다.
- **TFT Compass(상용) Pool Tracker 설명**: "Compass reads every player's board **and bench** in the lobby, so a champion someone else is holding shows as drained whether or not you have scouted them. Star levels are weighted properly — a 2★ is three copies, a 3★ is nine." + "If a count is marked **est.**, the **live bridge** is not currently supplying ground truth" → **상대 8명 보드+대기석 실시간 집계는 이미 상용 구현되어 있고, 그 소스는 "라이브 브리지"(GEP 계열) + 추정 폴백**이다.
- **TFT Compass 트러블슈팅**: `bridge/lock files` 언급, "an unsupported game build needs a compatible update" → **Riot 패치마다 브리지 호환 업데이트가 필요**한 게임 빌드 종속 구조.
- **NoxuTFT**: "everything it displays is based on what the game itself returns", 요구사항은 "Borderless/Windowed" + 해상도/언어 설정 불필요 → CV 방식이라기보다 브리지 방식 정황.
- **상대 증강·대기석에 대한 게임 내 노출**: 스카우팅 가이드는 "what augments people take"를 보고 lose streak을 깨라고 조언한다 → **상대 증강은 인게임에서 확인 가능한 정보**다(설계상 "숨겨진 정보"가 아니다).

### 그럼에도 남는 미확인 1건 (반드시 실측 필요)
`opponent_board_pieces` 가 **(a) 상대 7명 전부**인지 **(b) 내가 현재 관전 중인 1명**인지 문서 본문이 잘려 확인하지 못했다.
→ **다음 단계의 첫 실험(30분)**: 오버울프 개발자 확장을 띄워 게임 1판에서 그 값을 덤프하면 즉시 판정된다.
(a)면 CV를 거의 버려도 되고, (b)면 "관전당 1명"이므로 CV 어댑터가 필요하다.

## 3. 수학 판정 (여기는 검증 끝)

### 3.1 사용한 표준 모델
- 상점 5칸, 각 칸 독립. 한 칸: `레벨별 코스트 확률 × (대상 남은 사본 / 해당 코스트 등급 남은 사본)`.
- 리롤 1회 2골드. 3성 = 9사본, 2성 = 3사본(성급 가중치로 풀 소모 계산).
- Set 18 풀: 1코 30 / 2코 25 / 3코 18 / 4코 10 / 5코 9 (챔피언 1종당).

### 3.2 공개 벤치마크 재현 (실행 결과 그대로)
`python -m tftcalc.cli selftest`:

```
남은 사본 7 / 남은 4코 풀 137 -> 1칸 1.5%
1상점 확률 7.4% (공개값 7.4%)
   20골드 -> 53.8% (공개값 54%)
   30골드 -> 68.6% (공개값 69%)
   50골드 -> 85.5% (공개값 85%)
   60골드 -> 90.1% (공개값 90%)
다음 1장 기대 리롤 비용: 26.9골드
```
→ 공개 자료(tft.ninja)의 예시 수치와 일치. 즉 **파트 1의 계산 엔진은 신뢰할 수 있다.**

### 3.3 구상의 예시를 실제로 돌린 결과 (중요)
구상에서는 "3코 기물 겹침(남은 4개) → 3성 완성 예상 64골드"라고 썼다.
같은 상황(내 5장, 상대 9장, 3코 풀 18 → 남은 4장, 3성까지 4장 필요)을 Lv8에서 계산하면:

```
    3코확률     남은사본     1상점      기대리롤     예산내완성      기대총골드
   25.0%        4    2.1%     96.0g      0.3%     119.5g
   30.0%        4    2.5%     80.1g      0.7%     119.3g
   35.0%        4    2.9%     68.8g      1.2%     119.2g
```
→ **120골드를 전부 태워도 완성 확률 0.3~1.2%.** 남은 사본이 4장일 때 3성은 "비싼 도박"이 아니라 **사실상 불가**다.
계산기의 가치는 "64골드"라는 그럴듯한 숫자를 주는 게 아니라, **"이 라인은 접어라"를 즉시 말해주는 것**이다. (원 구상의 64골드는 이 현실을 가리고 있었다.)

### 3.4 구상의 Score 공식에 대한 판정
`Score = 현재 피통 + 소지 골드 − 메인 기물 완성 기회비용 ± 증강체 상성 점수` 는
- 피통(체력), 골드, 확률기대값(골드), 정성 점수를 **한 축에 더한다** → 차원 불일치.
- 가중치가 임의라서 결과(28%/72%)는 데이터가 아니라 **작성자의 취향**을 반영한다.
- "승률"로 표기하는 순간 캘리브레이션 없는 거짓 정밀도가 된다.

**대안(이 저장소가 택한 방식)**
1. 각 라인을 **(완성 확률, 기대 소모 골드)** 두 축으로 계산한다.
2. 한쪽이 두 축 모두 우세하면 **확률적 지배**로 결론을 낸다(가짜 승률 불필요).
3. 우열이 갈리면 **트레이드오프라고 말하고**, 결론에 필요한 누락 정보를 나열한다.
4. "골드 ↔ 승률" 환산은 **실측 캘리브레이션 이후에만** 도입한다(그 전에는 숫자를 만들지 않는다).
5. 모든 출력에 **데이터 신뢰도(스카우트한 상대 수)** 를 함께 붙인다.

### 3.5 인식/입력 오류를 다루는 방식 (`robustness` — "오류가 없다"가 아니라 "오류가 결론을 뒤집는가")

판단은 두 계층으로 나뉘고, **오류가 생기는 곳은 A층뿐**이다.

| 계층 | 내용 | 오류 가능성 |
|---|---|---|
| **A. 라벨링** | "이 아이콘은 Ahri, 2성, 아이템은 레드버프" 를 알아내는 단계 (CV / 수동 / GEP) | ⚠️ **여기서 오류가 난다** |
| **B. 계산** | 라벨이 주어지면 남은 사본·확률·기대 골드를 내는 단계 (이 저장소의 코어) | ✅ 결정적(오류 없음). 단 **모델 가정**은 있음 |

**A층 오류 원인 (경로별)**

| 경로 | 대표 오류 | 왜 |
|---|---|---|
| 화면인식(CV) | 오분류 / 미검출 | 아이콘이 비슷한 챔프, 스킨·증강 변형(같은 챔프 다른 아이콘), 별·아이템 겹침, 전투 이펙트·툴팁 가림, 해상도/UI 스케일(1920×1080 보더리스 전제), 임계값 트레이드오프(높이면 미검출↑, 낮추면 오분류↑) |
| 증강 인식 | 정확도 최저 | 6각형 프레임 + 애니메이션 배경 + 여러 크기 |
| 수동 입력 | 대기석 누락, 성급 오독(1성↔2성), 동일 계열 챔프 혼동 | 사람의 시선 처리 한계. **대기석을 빠뜨리면 남은 사본이 과대평가 → 낙관 편향** |
| GEP/브리지 | 미관전 상대 누락, 갱신 지연, 패치 후 버전 불일치 | 브리지가 ground truth를 못 주면 값이 추정치로 떨어짐(Compass의 `est.` 표기가 같은 문제) |

**B층(계산)의 정확성 정도**
- 정확: 확률·기대 골드·완성 확률(표준 상점 모델, 공개 수치 재현 완료).
- 가정(오차 방향이 반대라 상쇄되는 부분도 있음):
  - 상점 간 독립 가정 → 미세 편향
  - 내가 롤링하는 동안 **상대가 사본을 가져가는 효과 미반영** → **낙관 방향**
  - 라운드마다 오는 **무료 상점 제외** → **비관 방향**
  - 등급 전체 소모(tier in play)를 정확히 안 세면 → 낙관 방향

**그래서 넣은 장치: `robustness` (오차 내성 검사)**

상대 보유를 **±n장 틀렸다고 가정하고 전 구간을 다시 계산**해서, 결론이 유지되는지 본다.

```
python -m tftcalc.cli robustness --level 8 --cost 4 --own 1 --others 2 --tolerance 2 --budget 60

    상대보유     남은사본     1상점      예산내완성      기대총골드  결론
       0        9    9.3%      69.7%      43.7g  롤다운
       1        8    8.4%      62.5%      45.7g  롤다운
       2        7    7.4%      55.6%      47.8g  롤다운
       3        6    6.4%      46.6%      50.2g  전환 검토
       4        5    5.4%      36.7%      52.4g  전환 검토
[판정] 오차에 따라 결론이 뒤집힌다: 롤다운 / 전환 검토
       -> 경계 케이스다. 남은 사본을 한 번 더 확인(대기석 포함)한 뒤 판단해야 한다.

# 같은 조건에서 상대가 확실히 겹친 경우(±2장)
       3~7장 모두 '전환 검토'  →  [판정] 오차 범위 안에서 결론이 유지된다.
```

**읽는 법(중요)**
- 원시 확률은 오차에 민감하다: 남은 사본이 9→2장으로 줄 때 1장 차이가 완성 확률을 **69.7% → 62.5% → 55.6% → 46.6% → 36.7% → 25.9% → 15.7% → 6.4%** 로 흔든다. 특히 저사본 구간(3장→2장)은 1장 오차가 **2.5배** 차이다.
- 하지만 **결론은 안정적일 수 있다**: 남은 사본이 적은 구간(3~7장 모두 '전환 검토')에서는 스카우트가 1~2장 틀려도 "접어라"는 판단이 바뀌지 않는다.
- 즉 정직한 UX는 "정확도 100%"가 아니라 **"이 결론이 오차에 얼마나 견디는가"** 를 같이 보여주는 것이다.

**A층 오류를 줄이는 실제 완화책 (설계에 반영할 것)**
1. **신뢰도·불확실성 동시 표시**: 스카우트 n/7, 오차 범위 결론 안정성(`robustness`)을 항상 함께 낸다.
2. **미검출은 사용자가 확정**: CV 상용 툴도 "Confirm your board — tick the champions you actually have", "아이템을 손으로 추가할 수 있다"를 기능으로 둔다(모델이 못 본 것을 사람이 채움).
3. **라벨은 카탈로그와 1:1 자동 생성**: 아이콘↔이름 매핑은 CommunityDragon 등에서 기계적으로 만들어 **사람의 라벨링 실수 가능성을 제거**한다(세트 교체 때 재생성).
4. **모호하면 플래그**: CV에서 top-2 후보 점수 차(margin)가 작으면 "확인 필요"로 띄우고 자동 확정하지 않는다.
5. **사후 대조로 정확도 측정**: 경기 종료 후 `match-v1`의 실제 유닛/증강 데이터와 CV/수동 기록을 대조해 **경로별 오류율을 수치로 관리**한다(이게 없으면 "정확한 것 같다"에 머문다).

### 설계 원칙 3개 (구상과 다른 점)
1. **검증된 것과 미검증 것을 코드에서 분리한다.** `pool_math`/`lobby` 는 수학·데이터만. 보드 파워·증강 상성·메타는 **아예 없다**(있으면 거짓말이 되기 때문).
2. **모르는 게임 데이터는 추정하지 않는다.** 확률표에 없는 (레벨, 코스트)를 요구하면 `UnknownOddsError` 로 멈추고 "JSON에 채워 넣으세요"라고 알려준다. 추정으로 채우면 도구 전체의 신뢰가 무너진다.
3. **입력 출처는 어댑터다.** 수동 입력/화면인식/GEP 모두 `LobbySnapshot` 하나로 수렴한다. 수학 코어는 데이터가 어디서 왔는지 모른다 → **데이터 소스 교체가 코드 1개 파일 교체로 끝난다.**

### 알려진 한계 (도구가 스스로 밝히는 것)
- 상점 간 독립 가정(구매로 인한 풀 감소는 MC가 반영, 해석해는 '다음 1장' 근사)
- 내가 롤링하는 동안 **상대가 사본을 가져가는 효과는 미반영**
- 라운드마다 주어지는 **무료 상점(공짜 리롤) 제외** → 실제보다 보수적(비관적)
- 확률표는 현재 **부분 검증**(Lv8 4코 30%, Lv10/11 5코). 나머지는 사용자가 채워야 함
- 챔피언 이름↔코스트 매핑은 스냅샷에서 역추적(별도 카탈로그 없음)

## 5. 덱 효율 랭킹 (초점): "어떤 덱이 가장 싸게 완성되는가"

### 5.1 왜 "단일 기물 계산"으로는 부족한가
각 기물을 따로 계산하면 보통 **과대평가**된다. 예를 들어 컴프 5유닛이 각각 90%라면
"다 되겠네"라고 착각하지만, 실제로는 **같은 골드와 같은 상점 5칸을 공유**하므로
동시 완성 확률은 급감한다. 실측 예시(예시 스냅샷, Lv8, 80골드):

| 유닛 | 격리(그 유닛만) | 동시(컴프 전체) |
|---|---|---|
| Varus 2성 | 67.1% | 54.6% |
| Leona 2성 | 70.5% | 55.6% |
| Rakan 2성 | 80.7% | 67.7% |
| Karma 2성 | 93.7% | 86.8% |
| Sentry 2성 | 94.5% | 88.4% |

→ 그래서 이 도구는 **두 값을 항상 같이** 보여준다. 차이가 크면 "컴프가 너무 크다" 또는
"경쟁이 심한 유닛이 섞였다"는 신호다.

### 5.2 출력에 담는 3가지 (요청하신 초점 그대로)
1. **기물별 2성/3성 확률** — `outlook` 명령. 확률 + 성공 시 평균 소모 골드.
2. **컴프 동시 완성 확률 + 총비용** — `comp` 명령. **컴프별 롤 레벨**과 레벨업 XP 골드를 반영해
   `총비용 = 레벨업 + 리롤 + 구매`.
3. **랭킹** — 후보 컴프를 (동시 완성 확률 ↑, 총비용 ↓)로 정렬. "가장 싸게 구성되는 덱"이 1위.

### 5.3 실행 예 (실제 출력)

```
python -m tftcalc.cli outlook --odds-file data/set18_shop_odds_assumed.json ^
    --snapshot data/example_snapshot.json --level 8 --budget 150 ^
    --units Karma:4,Sentry:3,Leona:3,Warwick:3

기물              코   보유   남은     1상점      2성      2성기대골드      3성      3성기대골드
Karma           4    2    6    6.8%   99.5%       32.1g      0%           -  풀 부족(남은 6 < 필요 7)
Sentry          3    2   14    7.1%    100%       29.9g    7.8%      126.2g
Leona           3    1   13    6.6%   94.8%       61.8g   1.40%      133.9g
Warwick         3    0   17    8.6%   93.2%       74.8g   2.43%      131.2g
```
읽는 법: **2성은 150골드로 거의 되지만, 3성은 같은 골드로 1.4~7.8%** 다.
"3성 가자"는 판단이 얼마나 비싼 도박인지가 숫자로 드러난다.

```
python -m tftcalc.cli comp --odds-file data/set18_shop_odds_assumed.json ^
    --snapshot data/example_snapshot.json --comps data/comps_set18.json ^
    --gold 150 --levelup-from 7 --levelup-rounds 6

현재 레벨 Lv7 -> 컴프별 목표 레벨까지 XP 골드 계산 (패시브 XP 6라운드 반영)
기대총골드 = 레벨업 + 리롤 + 구매 (즉 '이 덱을 완성하는 데 드는 총 골드')
성공시 = 실제로 완성했을 때의 평균 소모. '-' 는 성공 사례가 없다는 뜻(사실상 불가).
  순위 컴프                     Lv  유닛    동시완성   기대총골드    성공시   레벨업    리롤    구매  비고
   1 예시) 카르마 4코 밸류           8   5    33.5%   143.9g  132.9g  48.0g  72.5g  23.4g
   2 예시) 유나라 4코 캐리           8   4    19.8%   147.1g  137.1g  48.0g  74.7g  24.4g
   3 예시) 3코 리롤               6   3    0.03%   149.5g  138.0g   0.0g 119.3g  30.2g
```

### 5.5 A단계: 컴프별 롤 레벨 + 레벨업 골드 정산
레벨이 다른 덱을 같은 기준으로 비교하려면 **레벨업 골드가 롤 예산을 잠식**하는 것을 반영해야 한다.

* 컴프 JSON의 `"level"` = 그 컴프를 굴릴 레벨(리롤덱 6~7, fast-8 8). 없으면 CLI `--level`.
* 컴프 JSON의 `"target_star"` = 기본 성급, `units[].target_star` 로 유닛별 덮어쓰기.
* `--gold N`(총 보유 골드) 모드: **`N − 레벨업비용 = 롤/구매 예산`**. 위 표에서 Lv6 리롤덱은
  레벨업 0골드로 119골드를 전부 롤에 쓰고, fast-8 덱은 48골드를 레벨업에 먼저 내고 72골드로 롤한다.
* `--budget N` 모드(구식): 롤 예산을 따로 주고 레벨업 비용은 총비용에만 가산.

**이 표가 말해주는 것(실측)**
- 같은 150골드에서 **fast-8 밸류덱 33.5%** vs **3코 리롤(3성 2개) 0.03%**.
  "리롤 가자"가 이 로비·이 골드에서는 사실상 불가라는 뜻이다.
- 리롤덱의 롤 예산(119g)이 밸류덱(72g)보다 큰데도 확률이 낮은 이유는 **3성이 9장씩 필요**하고
  경쟁(Leona 소모 5장)이 있기 때문 → 레벨업 골드만 보면 안 되고 목표 성급을 같이 봐야 한다.
- `성공시` 열이 `-` 이면 성공 사례가 없다는 뜻이다(예산을 다 태우고도 못 이룸).

### 5.4 정직하게 남기는 경계
* **컴프 목록은 입력이다.** 이 도구는 "무엇이 메타인가"를 만들지 않는다. `data/comps_set18.json`
  에 채워 넣으면 그 후보들 중 **지금 이 로비에서 가장 싸게 완성되는 것**을 계산해준다.
  컴프마다 `level`(롤 레벨)과 `target_star`(목표 성급)를 적는다. 예시 파일은 `verified: false` 로
  표시해 두었고, 출력에도 `[미검증 컴프 데이터]` 가 찍힌다.
* **아이템(부품) 수급은 미반영.** 그래서 "완성 확률이 높은 덱"이 곧 "좋은 덱"은 아니다.
  아이템까지 반영하려면 부품 수급 경로 모델이 별도로 필요하다(2차 범위).
* **레벨업 골드**는 `tft.ninja`의 누적 XP 표(3레벨 2 … 10레벨 270)에서 계산한다. 패시브 XP는
  `--levelup-rounds` 로 명시할 때만 차감한다(기본은 보수적 상한).
* **증강 상성/승률**은 Riot 정책상 표시 금지라 넣지 않았다.

유닛 **코스트는 전부 자동 수집으로 검증**했다.

매핑(예: 불타는 묘목 = Cinderling = 협곡야수+사냥꾼)도 추정이 아니라 특성 개수로 확인된 것이다.

**갱신 자동화** (메타는 2주 단위로 바뀐다):

```
→ 컴프에 유닛을 추가/교체하고 위 명령만 돌리면 **코스트가 틀릴 위험 없이** 갱신된다.

읽는 법(실전적):
- **200골드가 있어도 8유닛 4코 덱은 동시 완성이 2~7%** 다(소라카 덱·니달리 덱). "각 유닛 99%니까 되겠지"가 통하지 않는다.
- **아리 모르가나가 1위**인 이유는 필요한 유닛이 6개(카르마·조약돌은 이미 2성 보유)이고 경쟁이 상대 1명뿐이기 때문 → 같은 골드에서 **가장 싸게 완성되는 덱**이라는 뜻이다.
- 리롤덱은 레벨업 골드가 0이라 리롤 예산(159.8g)이 가장 큰데도 확률이 낮다 → **1코 3성(9장) + 3코/5코 유닛**을 함께 요구하기 때문. "리롤이 싸다"는 통념이 조건부임을 보여준다.

### 5.7 C단계: 아이템 부품 수급 모델 ("유닛은 되는데 아이템이 안 맞는 덱")

**문제**: 유닛 확률만으로 랭킹하면 "아이템이 안 맞는 덱"이 1위로 올라온다. 아이템은 부품 2개가
합쳐져 완성되므로, **부품 수급 자체를 계산**해야 한다.

**사용한 데이터 (전부 출처 검증)**
* 조합식 31개: `tft.ninja/items/<slug>` 페이지의 부품 이미지(`DA_Component_*`)를 파싱해 생성
  → `python scripts/fetch_item_recipes.py` (생성물: `data/set18_item_recipes.json`)
  → 파서 검증: Deathblade=검+검, Infinity Edge=검+장갑, Guinsoo=큰지팡이+활, Warmog=벨트+벨트 등 **공개 조합식과 전부 일치**
* 캐리별 코어 아이템: 덱 공략의 추천 아이템(예: 아리 → 보석 건틀릿·푸른 파수꾼·라바돈)을
  `comps_set18.json` 의 `items.core`(우선순위 순)에 기입

**실행 결과 (아리 모르가나, 코어 6개 기준)**
```
필요 부품: Giant's Belt x1, Needlessly Large Rod x3, Recurve Bow x3, Sparring Gloves x1, Tear of the Goddess x4
보유 부품: B.F. Sword x1, Needlessly Large Rod x2, Recurve Bow x1, Sparring Gloves x1, Tear of the Goddess x1
지금 부족: Giant's Belt x1, Needlessly Large Rod x1, Recurve Bow x2, Tear of the Goddess x3
부품 우선순위(캐러셀/모루에서 이걸 집는다): Tear of the Goddess x3 > Recurve Bow x2 > Giant's Belt x1 > Needlessly Large Rod x1
앞으로 부품 6개(+선택 2개)를 받으면 전부 완성될 확률: 3.1%
그때도 평균 2.43개 부품이 부족하다
```
→ **6개 코어 아이템(부품 12개)을 다 맞추는 확률은 3.1%**. 아이템은 유닛보다 더 빡빡한 제약이다.

**랭킹에 붙이면 (아이템 축 + 결합 열)**
```
  순위 컴프                     Lv 유닛   동시완성    아이템     결합    기대총골드
   1 아리 모르가나                 8   6    65.2%    100%   65.2%   175.0g   (코어 3개 기준)
   2 선봉대 아펠리오스               8   8    10.8%    100%   10.8%   198.5g
   3 니달리 시비르                 8   8     7.1%    100%    7.1%   199.0g
   4 날렵이 베이가 (1코 리롤)         6   7     6.6%    100%    6.6%   198.1g
   5 소라카 말파이트 자이라            8   8     2.58%      -       -    199.3g  (아이템 데이터 없음)
```
* `아이템` = 지금 + 앞으로 받을 부품으로 **코어 아이템이 다 맞을 확률**
* `결합` = 유닛 완성확률 × 아이템 확률 (**두 조건이 모두 성립할 확률, 독립 가정**)
* `--core-items-limit` 로 코어를 몇 개까지 볼지 정한다(기본 3~6이 현실적. 0=전부)

**모델 가정(명시)**
* 무작위 부품은 **8종 균등**으로 떨어진다(실제론 약간의 가중이 있을 수 있음).
* 캐러셀/모루/아이템 증강처럼 **골라 받는** 부품은 `--choice-components` 로 세며,
  아무 부족분이나 메우는 와일드카드로 취급한다.
* 모으는 동안 부품을 다른 아이템에 쓰지 않는다(코어에 우선 투자).
* 유닛당 3칸 제약은 '코어 아이템 개수'로 이미 반영된다(core-items-limit).

**실전적 결론**: 코어를 6개 다 맞추는 건 3%. 그래서 이 도구는 **"코어를 몇 개로 좁힐지"를
숫자로 보여준다**(아이템 100%가 되는 개수까지 내려서 판단). 이게 "아이템까지 맞는 덱" 판단의 근거다.

### 5.8 D단계: 라운드 수입 / 롤 타이밍 ("4-2에 몇 골드로 이 덱이 되나?")

유닛(공간)과 아이템(부품)에 이어 **시간** 축을 붙였다. 골드는 라운드마다 들어오고, 레벨업은 그 골드를 먹는다.

**수치 출처 (전부 문서화된 값)**
| 항목 | 값 | 출처 |
|---|---|---|
| 기본 수입 | 1-2=2, 1-3=2, 1-4=3, 2-1=4, **2-2부터 5** | tft.ninja economy |
| 이자 | 보유 골드 // 10, **최대 5**(50골드 이상) | tft.ninja economy |
| 스트릭 | 2~4연속 +1, **5연속 +2, 6연속 이상 +3** | tft.ninja economy |
| PvP 승리 | **+1골드** (스트릭과 별개로 중첩) | tft.ninja economy |
| 라운드 구조 | X-1~X-3 PvP, **X-4 캐러셀**, X-5~X-6 PvP, **X-7 PvE** | tft.ninja stages |
| PvE 오브 골드 | 공개 수치 없음 → `--pve-gold`(기본 3, 가정임을 출력에 표시) | — |

**실행 예 (3-5 / 60골드 / Lv6 / 3연승 / 4-2에 8레벨 목표)**
```
   라운드       유형   기본   이자    스트릭    승리  PvE     수입    레벨업     종료골드     롤예산   레벨
   3-5      PvP    5    5      1   0.5    0   11.5      0       71      71    6
   3-6      PvP    5    5      1   0.5    0   11.5      0       82      82    6
   3-7      PvE    5    5      2   0.0    3   15.0      0       97      97    6
   4-1      PvP    5    5      2   0.5    0   12.5      0      109     109    6
   4-2      PvP    5    2      3   0.5    0   10.5     88       31      31    8
   4-3      PvP    5    3      3   0.5    0   11.5      0       42      42    8
   4-4 Carousel    5    4      3   0.0    0   12.0      0       54      54    8

요약: 3-5 -> 4-5 / 총수입 98.0골드 / 총 레벨업 지출 88골드 / 최종 67골드 Lv8
[4-5 시점] 보유 67골드 / Lv8 / 리롤·구매 예산 67골드
```
읽히는 것(실전적):
* **Lv6 → Lv8 레벨업이 88골드**(누적 XP 96 − 패시브 XP 8). 4-2에 8레벨을 찍으면 리롤 예산이 **31골드**로 줄고,
  4-5까지 기다리면 67골드가 된다 → "빠른 8레벨 + 즉시 리롤"과 "한 라운드 더 세이빙"의 트레이드오프가 숫자로 보인다.
* 이자 5골드(50+)를 유지한 채 3-7 PvE(+15골드)와 4-1(+12.5골드)만 넘겨도 109골드 → **4-1에 7레벨, 4-2에 8레벨**이 가능한 이유.

**그 시점 예산으로 컴프 판정까지 (같은 명령에 `--comps`)**
```
=== 4-5 예산 67골드로 컴프 판정 (Lv8, 레벨업 비용은 이미 반영됨) ===
  순위 컴프                     Lv 유닛     동시완성     아이템      결합
   1 아리 모르가나                 8   6       0.67%    100%      0.67%
   2 선봉대 아펠리오스               8   8          0%    100%         0%
   ...
```
→ **"지금 이 골드/타이밍으로는 6유닛 4코 컴프가 사실상 안 된다"** 는 결론. 목표를 낮추거나(코어 축소)
라운드를 더 세이빙해야 한다. 반대로 `--gold 200` 시점에서는 아리 모르가나가 33~66%가 나온다(5.6절).

**`--need-gold` 로 필요 골드 대비 판정**
```
[4-2 시점] 보유 73골드 / Lv7 / 리롤·구매 예산 73골드
[필요 골드 판정] 필요 130골드 vs 예산 73골드 -> 부족 (57골드 부족: 세이빙 라운드를 늘리거나 목표를 낮춰야 한다)
```

**모델 가정(명시)**
* 승리 여부는 모르므로 **기대값**(`--win-rate` × 1골드, 기본 50%)으로 계산한다. 실제로는 이기면 +1, 지면 +0.
* 스트릭은 기본 "유지" 가정(`--streak-behavior reset` 으로 보수적 계산 가능).
* 이자는 **그 라운드 지출 후** 남은 골드로 계산한다(게임과 동일).
* 레벨업 비용은 흐른 라운드의 **패시브 XP(2/라운드)를 반영**한다.

### 5.9 E단계: 체력/피해 축 — "리롤 vs 전환"의 진짜 손익분기

골드만 보면 "세이빙이 항상 이득"이지만, 세이빙하다 **죽으면** 그 골드는 의미가 없다.
그래서 체력을 자원으로 계산한다.

**피해 공식 (출처: tft.ninja player-damage-calculation, 패치 18.1)**
```
총 피해 = 스테이지 기본 피해 + 살아남은 상대 유닛 수
기본 피해: 1=0, 2=2, 3=5, 4=8, 5=10, 6=12, 7+=17
살아남은 유닛은 성급/코스트 무관 1개당 1 피해, 시작 체력 100
문서 예시: 3스테이지 5유닛=10 / 4스테이지 6유닛=14 / 6스테이지 9유닛=21 / 7스테이지 9유닛=26
```
→ 테스트에서 이 4개 예시를 **그대로 대조**한다(공식 구현이 맞다는 증거).
→ 문서의 경험칙(60HP/4스테이지→4회, 40HP/5스테이지→2회, 25HP/6스테이지→1회)도 함께 검증한다.

**실행 예 (4-1 / 38HP / 승률 35% / 목표 4-5)**
```
  지금 체력으로 감당 가능한 패배 횟수(근사): 2회
   라운드       유형     기본피해     기대피해     기대체력     생존확률
   4-1      PvP        8     10.2     27.8     100%
   4-2      PvP        8     10.3     17.5    99.4%
   4-3      PvP        8     10.3     13.3    73.1%
   4-4 Carousel        8      0.0     13.3    73.1%
   4-5      PvP        8     10.3     11.2    44.5%
[4-5] 생존확률 44.5% / 기대 체력 11.2HP / 기대 사망 라운드 4-4
```

**핵심 출력: 안정화(롤) vs 세이빙 비교**
```
=== 지금 안정화(롤) vs 그대로 세이빙 ===
  세이빙 유지      승률 35% / 생존  44.5% / 기대 체력  11.2 / 4-5 골드 120
  지금 40골드 롤   승률 60% / 생존  82.3% / 기대 체력  18.0 / 4-5 골드  78
  판정: 트레이드오프: 지금 40골드 롤 는 생존확률 +37.8%p, 대신 목표 라운드 골드가 42골드 적다.
  교환비율: 생존확률 1%p 당 1.1골드
  결론에 필요한데 아직 없는 정보:
    - 롤 후 실제 승률 변화(경험치 필요: 롤 전/후 승률 기록)
    - 남은 상대 보드 강도(스카우팅 정확도)
    - 증강/수호령으로 인한 추가 골드·체력 효과
```
→ 처음 구상의 "리롤 28% vs 전환 72%"를 **가짜 숫자 없이** 대체하는 형태다.
"생존확률 37.8%p 를 42골드에 사는 셈(1%p당 1.1골드)" 이라는 **사실**만 제시하고,
한쪽이 두 축 모두 우세할 때만 결론(지배)을 낸다.

**모델 가정(명시)**
* 승률은 입력값(`--win-rate`, 롤 후는 `--win-rate-roll`). 이 값의 캘리브레이션만이 남은 과제다.
* 패배 시 남는 상대 유닛 수는 평균 `--enemy-survivors`(기본 8)의 정규분포로 흉내낸다.
* PvE/캐러셀 라운드는 피해 0 가정(`--pve-damage`).
* 피해는 라운드마다 독립(연속 패배 시 추가 페널티 없음).

```
[5] 권장 동선(규칙 기반): 세이빙 연장 또는 목표 하향 — 50골드 부족

    근거: 4-2 생존확률 99.0%             <- HP는 문제가 아니다
    근거: 필요 골드 60 vs 예산 10
    교환비율: 생존확률 1%p 당 46.7골드      <- 여기서 롤은 무의미(이미 안 죽는다)
```
→ **HP가 넉넉하면 "체력 때문에 롤"이 아니라 "골드가 없어서 못 굴린다"** 는 진단이 나온다.
이게 축을 나눠 계산하는 이유다(축을 합쳐 한 점수로 만들면 이 구분이 사라진다).

**권장 동선 규칙 (모두 출력에 근거를 함께 표시)**
1. 롤이 생존확률을 10%p 이상 올리고 지금 생존확률이 50% 미만 → **안정화 롤 우선**
2. `--need-gold` 대비 예산 부족 → **세이빙 연장 또는 목표 하향**
3. 1순위 컴프 유닛 완성확률 ≥ 50% → **목표 라운드에 계획대로 리롤**
4. 목표 라운드 생존확률 < 40% → **체력 리스크 경고(안정화 또는 목표 앞당김)**
5. 그 외 → **관망(세이빙 유지, 다음 라운드 재평가)**

**실전 사용 순서(권장)**
1. **최초 1회 준비**: `scripts/build_templates.py --from-comps data/comps_set18.json` (아이콘 템플릿)
   + `scripts/check_capture.py --out shot.bmp` 로 좌표 확인(필요하면 `data/layout_1920x1080.json` 보정)
2. **매 라운드**: `report --scan ...` 한 줄
   (라운드/골드/레벨/HP/스트릭 + 스캔 + 컴프/확률표 + 부품 입력)
3. `[5]`의 권장 동선과 근거를 읽고 판단(도구는 결정을 대신하지 않는다)
4. 상세가 필요할 때만 개별 명령: `outlook`(기물별 확률), `items`(부품), `plan`(골드), `survive`(체력), `comp`(덱 랭킹), `scan`(스캔만)

### 5.11 CV 어댑터: 화면에서 입력 자동으로 긁어오기

수동 입력이 실전 병목이라는 걸 알고 있었으니, 화면 인식을 붙였다. **외부 패키지 0개**
(PIL/numpy/cv2/mss 없이 표준 라이브러리 + ctypes GDI)로 구현했다 — `pip install` 없이 바로 돈다.

**구조**
```
tftcalc/cv/screen.py       화면 캡처(GDI, ctypes) + BMP 저장/로드(직접 구현) + 창 찾기
tftcalc/cv/fingerprint.py  아이콘 지문(8x8 정규화 그레이스케일) + 분류 + 마진 정책
tftcalc/cv/layout.py       1920x1080 기준 좌표(비율 정의, JSON 오버라이드 가능)
scripts/build_templates.py Data Dragon 아이콘 -> 템플릿, 또는 화면 크롭 -> 템플릿
scripts/check_capture.py   캡처 확인 + 좌표 디버그(BMP 저장) + 인식 시험
scripts/crop_slots.py      벤치/상점 칸 크롭 저장(TFT 전용 유닛 라벨링용)
```

**왜 슬라이딩 템플릿 매칭이 아니라 '칸 분류'인가**: TFT UI 좌표는 고정이다(벤치 9칸, 상점 5칸).
그래서 화면 전체를 훑을 필요 없이 칸을 잘라 NxN 지문으로 줄이고 후보와 거리만 재면 된다 →
순수 파이썬으로 충분히 빠르고, 외부 의존성이 사라진다.

**실제로 검증된 것 (이 PC, Windows 1920x1080)**
```

  분산(검은 화면 판별): 10230.7 (0에 가까우면 캡처 실패 의심)   <- 실제 캡처 성공
  저장: shot.bmp

* **자기 분류 100% / 평균 마진 0.354**: 템플릿이 서로 잘 구분된다는 뜻(오분류 위험 챔피언은 자동으로 "확인 필요"로 표시됨)

**TFT 전용 유닛 보충 (Krug, Pebbles, Cinderling …)**
```powershell

# 파일 이름을 유닛 이름으로 바꾼다: shop_3.bmp -> Krug.bmp

```

**정직하게 말할 한계 (중요)**
1. **게임 화면에서의 정확도/좌표는 아직 검증하지 못했다.** 이 환경에 TFT 게임 화면이 없기 때문이다.
   좌표(`layout.py`)는 공개된 UI 배치를 바탕으로 넣은 **기본값**이고, `check_capture.py`로 저장한
   BMP를 보며 `data/layout_1920x1080.json`으로 보정하는 절차를 문서화해 두었다.
2. **성급(1/2/3성) 별 인식은 골격을 구현했지만 기본 꺼짐이다.** 별 영역의 밝은 비율은 아이콘
   자체와 섞이기 쉬워(실측: 별 1개 면적의 약 12배) 실게임 화면에 맞추기 전에는 1성을 2성으로
   읽는 식의 **3배 오차**가 날 수 있다. `--star-ocr` 로 켜되, 안전하게는 `--star 'Ahri=2'` 로 지정한다.
3. **숫자(골드/레벨/HP)와 라운드('4-2') OCR 골격은 있다**(`cv/ocr.py`: 자릿수 분리 + 지문 분류,
   라운드는 '숫자·구분자·숫자' 3조각이고 범위(1~9 / 1~7) 안일 때만 확정). 다만 `--digits` 로
   0~9 지문 파일을 주지 않으면 읽지 않고 `None` + '손 입력 필요' 다(그 파일은 실게임 숫자 크롭으로
   만들어야 한다).
4. **상대 보드/대기석은 읽지 않는다.** 이 도구는 내 화면만 본다(상대는 스카우팅/GEP 입력).
5. 빈 칸은 `unknown`으로 남긴다(추정 금지). 마진이 작으면 자동 확정하지 않고 "확인 필요"로 표시한다.

### 5.12 CV → 계산기 연결: "한 번 실행하면 끝"

5.11에서 만든 인식을 **계산기에 직접 연결**했다. 이제 화면(또는 저장된 BMP)을 읽어 내 보드/벤치를
자동 입력하고, 그대로 리포트를 뽑는다.

**두 가지 사용법**
```powershell
# (A) 스캔만: 스냅샷 파일 생성
python -m tftcalc.cli scan --templates data/templates_set18.json ^
    --in shot.bmp --area bench,shop --out data/my_board.json --keep-opponents data/lobby.json
   
# (B) 한 번에: 스캔 + 통합 리포트  ← 실전은 이 한 줄
python -m tftcalc.cli report --round 4-1 --gold 60 --level 7 --hp 40 --streak -3 ^
    --target-round 4-5 --levelup 4-2:8 --roll-gold 40 ^
    --scan --templates data/templates_set18.json --scan-out data/my_board.json ^
    --snapshot data/lobby.json --comps data/comps_set18.json ^
    --odds-file data/set18_shop_odds_assumed.json ^
    --components rod:2,gloves,tear --future-components 6
```
* `--scan` 은 **내 보드/벤치/상점**을 채운다. 상대는 `--snapshot`(기존 스냅샷)에서 **보존**된다(상대는 화면 스캔 영역이 아님).
* **상점 칸은 '보유'로 세지 않는다.** 스냅샷에 `shop` 으로 따로 담기고 풀 계산(`board`/`bench`)에는 안 들어간다 —
  상점에 보이는 기물은 아직 사지 않은 것이라, 보유로 세면 내 보유가 과대평가되고 남은 풀이 과소평가되어
  판정이 **낙관 편향**된다. 지금 산다고 가정해 모델링하려면 `--shop-as-owned` 를 붙이고, 그러면 `[가정]` 이 출력된다.
* `--scan-in <BMP>` 로 게임 없이도 스캔 경로를 시험할 수 있다.
* **성급(별)은 기본적으로 읽지 않는다**(1성 + 고지). `--star-ocr` 로 켜면 별 개수를 세지만,
  임계값을 실게임 화면에 맞추기 전에는 애매/과대 비율을 `[확인 필요]` 로 빼기만 하므로
  안전하게는 `--star 'Ahri=2,Krug=3'` 로 지정한다.
* **숫자(골드/레벨/HP)와 라운드('4-2')는 `--digits <0~9 지문 JSON>` 을 줄 때만 읽는다.** 없으면
  전부 `None` + '손 입력 필요'다(0 으로 추정하지 않음). 읽힌 값은 요약의 `[정보]` 줄에 나온다.

**실제 아이콘으로 끝까지 검증한 결과** (게임 화면 대신 실제 Data Dragon 아이콘을 상점 좌표에 붙여 시험)
```
python scripts/simulate_scan.py --units ahri,morgana,sett,karma --out sim_shot.bmp
[붙임] shop_1 ahri (Ahri.png) / shop_2 morgana / shop_3 sett / shop_4 karma

python -m tftcalc.cli scan --templates data/templates_set18.json --in sim_shot.bmp --area shop
=== 화면 스캔 결과 ===
인식 확정 4칸 / 확인 필요 1칸 (신뢰도 80%)
  [확정] shop_1  Ahri     4코 (유사도 97.1%)
  [확정] shop_2  Morgana  4코 (유사도 96.6%)
  [확정] shop_3  Sett     4코 (유사도 95.7%)
  [확정] shop_4  Karma    1코 (유사도 95.5%)
  [확인 필요] shop_5  빈 칸/미등록
  [영역] 보드 0칸 / 벤치 0칸 / 상점 4칸
  [상점] Ahri, Morgana, Sett, Karma — 상점 칸은 '보유'가 아니므로 풀 계산에 넣지 않았습니다(사면
  즉시 보유가 되니 그때 다시 스캔하거나 --shop-as-owned).
  ※ 성급은 1로 기록했습니다(아이콘으로는 못 읽음)
```
→ 실제 아이콘 인식 **유사도 95~97%**, 이름·**코스트까지 정확**(Karma 1코, 나머지 4코), 빈 칸은 자동 분리.
→ 그리고 `report --scan` 한 줄로 이 결과가 **리포트 [1]~[6]에 그대로 반영**된다.

**정직성 장치(스캔에도 동일 적용)**
| 상황 | 도구의 행동 |
|---|---|
| 빈 칸 / 미등록 아이콘 | `unknown` → 스냅샷에 안 넣고 "확인 필요"로 보고 |
| 두 챔피언이 비슷해 마진이 작음 | 자동 확정하지 않고 `runner_up`(2등 후보)와 함께 "확인 필요" |
| 코스트를 모르는 유닛(TFT 전용) | 스냅샷 제외 + `missing_cost` 로 어느 유닛인지 알림 |
| 성급(1/2/3성) | 별 개수를 세어 읽되 **기본 꺼짐**(아이콘 오염으로 3배 오차 위험). 켜면 애매/과대 비율은 확정하지 않고 `[확인 필요]` 로 뺀다. `--star 'Ahri=2'` 지정이 항상 우선 |
| 숫자(골드/레벨/HP) · 라운드 | `--digits` 가 없거나 못 읽으면 `None` + '손 입력 필요'(0 으로 추정하지 않음). 라운드는 조각 3개(숫자·구분자·숫자)이고 범위 안일 때만 확정 |
| **상점 칸** | **'내 보유'가 아니다** → `shop` 키로 분리해 풀 계산에서 제외(상점에 보이는 건 아직 안 산 것). 지금 산다고 가정하려면 `--shop-as-owned` 로 **명시**하고 그 사실을 `[가정]` 으로 고지 |

**남은 한계(게임에서 쓸 때 반드시 확인)**
1. **좌표 캘리브레이션**: `layout.py` 기본값은 공개 UI 배치 기반 추정이다. `check_capture.py --out shot.bmp`로
   실제 게임 화면을 저장 → `data/layout_1920x1080.json` 오버라이드로 보정(1회).
2. **성급·숫자(골드/레벨/HP) 미인식**: 골드/레벨/HP는 아직 손으로 넣는다(`layout.INFO_REGIONS`에 자리만 있음).
3. 게임의 아이콘은 비용 테두리·발광이 있어 Data Dragon 아이콘과 조금 다르다 → 실제 화면에서
   `crop_slots.py` 로 딴 크롭으로 템플릿을 만들면 이 차이까지 흡수된다(`--from-crops`).

## 7. 세트 교체 유지비 경고 (1인 개발의 최대 리스크)

- 2~3개월마다 세트가 바뀐다 → 챔피언 아이콘, 아이템(최근 세트 기준 200종 이상), 증강 아이콘 템플릿이 **전량 교체**된다.

- 따라서 **CommunityDragon 등에서 아이콘/카탈로그 자동 수집 + 템플릿 자동 생성 파이프라인**을 초기에 깔지 않으면, 세트마다 수 주가 날아간다. 이건 "있으면 좋은 것"이 아니라 **지속 가능성의 전제조건**이다.

## 8. 아직 검증하지 못한 것 (정직하게 남겨둔다)

1. `opponent_board_pieces` 의 범위(전체 8명 vs 관전 1명) — 문서 중간이 잘려 확인 불가 → **W4 실험에서 확정**.
2. 상대 **대기석**이 화면에 노출되는지(예시 스냅샷은 노출 가정). 노출되지 않으면 남은 사본은 **과소평가**되므로 신뢰도 경고가 더 중요해진다.
3. 3코 등 나머지 확률 셀(패치마다 변동). 현재 검증된 셀은 (8,4)=30%, (10,5)=25%, (11,5)=35% 뿐이다.
4. match-v1 의 실제 지연/레이트리밋(개인 키 기준 실측 필요) — 배포 시에는 프로덕션 키 심사 대상.
5. 증강 "전투형/경제형" 분류의 타당성 — Riot이 공식 태그를 제공하지 않으므로 **자체 라벨링**이며, 승률 기반 지표는 정책상 금지다.
6. **컴프 목록의 신선도** — B단계에서 실제 메타 덱 4개를 넣었지만, **티어리스트는 패치마다 바뀐다**(출처 기준 패치 18.2b).
   유닛 코스트는 스크립트로 갱신되지만, "무엇이 S티어인가"와 "각 덱의 목표 성급/레벨"은 사람이 재확인해야 한다.
   → 갱신 주기와 담당(수동 vs 스크래퍼)을 정하는 것이 다음 운영 과제다.
7. **아이템 수급 모델의 가정** — 무작위 부품 8종 균등, 선택 부품=와일드카드로 계산한다. 실제로는
   스테이지별 드랍 구성·아이템 모루/증강 비중이 달라 확률이 움직인다. 또 **어느 유닛에 어떤 아이템을
   몰아주는지(아이템 배분 최적화)** 는 다루지 않는다(코어 목록을 우선순위로 자르는 것까지만).
   → 캘리브레이션(실제 경기에서 부품 수 로그)으로 분포를 맞추는 것이 다음 과제.
8. ~~**컴프별 롤 레벨**~~ → **✅ A단계에서 해결**(5.5). 컴프 JSON `level`/`target_star` + `--gold` 모드.
   ~~**아이템 수급 미반영**~~ → **✅ C단계에서 해결**(5.7).
   남은 것: 컴프마다 **중간 전환(board pivot)** 과 **수호령/증강 선택까지 포함한 골드 계획**은 모델링하지 않는다.
9. **수입 모델의 가정** — PvE 오브 골드(기본 3)는 공개 수치가 없어 가정값이고, 승리 보너스는 기대값(승률)으로
   계산한다. 스트릭은 기본 '유지' 가정이다. → 실경기 로그(라운드별 골드 변화)로 캘리브레이션하면 더 정확해진다.
10. ~~**보드 파워/체력 손실**~~ → **✅ E단계에서 해결**(5.9). 피해 공식 + 생존확률 + 안정화 vs 세이빙 비교.
    남은 것: **승률(`--win-rate`)의 캘리브레이션** — 지금은 입력값이다. 실경기에서 "롤 전/후 승률"을 기록하면
    이 값이 실측으로 대체되고, 그때 교환비율(1%p당 몇 골드)이 개인화된 판단 기준이 된다.
11. **CV 어댑터의 실제 게임 화면 검증** — 캡처/크롭/지문/템플릿 파이프라인은 이 PC에서 검증했지만,
    **TFT 게임 화면의 좌표값과 인식 정확도는 실측하지 못했다**(환경에 게임 화면 없음).
    `scripts/check_capture.py --out shot.bmp` 로 화면을 저장해 좌표를 보정하고, 인식 결과를 사후
    `match-v1` 데이터와 대조해 정확도를 수치로 관리해야 한다.
12. **성급(별)·숫자(골드/레벨/HP) 인식 미구현** — 아이콘은 읽지만 별/숫자는 아직 못 읽는다.
    같은 지문 방식으로 별·숫자 템플릿을 만들면 붙는다(좌표는 `layout.INFO_REGIONS`에 자리만 잡아둠).
